## 1. 全体構成

```
┌──────────────────────────────────────────────────────────────┐
│ ブラウザ（Web UI）※Tailscale経由でMacBook/iPhoneからも      │
│  ・URLを貼る → プロトコル自動判定バッジ                       │
│  ・エンコード設定（既定値入り）／オーバーレイ                 │
│  ・稼働中ジョブとログのライブ表示（SSE）                      │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP / SSE（127.0.0.1:8080 にバインド）
┌───────────────▼──────────────────────────────────────────────┐
│ API サーバー（FastAPI / Mac mini 上で launchd 常駐）          │
│  ├ Target Resolver … URL → プロトコル判定 + パラメータ分解   │
│  ├ Template Store  … エンコード条件の自動保存・LRU整理       │
│  ├ Source Store    … ローカルファイル / 外部ライブ / testsrc  │
│  ├ Command Builder … 上記 + オーバーレイ → FFmpeg引数を生成  │
│  ├ Job Runner      … 単一ジョブの起動・監視・再接続・停止    │
│  └ Log Pipeline    … stderr を解釈して構造化 + エラー翻訳    │
└───────────────┬──────────────────────────────────────────────┘
                │ プロセスグループ単位で起動 / SIGTERM で停止
┌───────────────▼──────────────────────────────────────────────┐
│ FFmpeg 9.0.1（libsrt・WHIP・drawtext 有効）                   │
└───────────────┬──────────────────────────────────────────────┘
                │
       RTMP / SRT / WHIP のいずれか 1本
```

### 技術選定と理由

| レイヤ | 選定 | 理由 |
|---|---|---|
| API | FastAPI (Python 3.13) | プロセス管理・SSE・非同期が素直に書ける。Homebrewのpythonで完結する |
| DB | SQLite | 単一ユーザー・単一プロセス。運用コストゼロ。移植時もファイルを持っていくだけ |
| フロント | 素のHTML + JS（ビルド不要） | 既存の analyzer 系と同じ方針。内部ツールにビルドパイプラインを持ち込まない |
| 送出 | `homebrew-ffmpeg/ffmpeg` tap版 FFmpeg 9.0.1（`--with-openssl@3`／libsrt / libx264 / freetype / VideoToolbox 有効） | RTMP・SRT・WHIP・drawtext を1本で賄える。検証済み（`環境検証メモ.md`） |
| WebRTC送出 | FFmpeg の WHIP muxer（`-f whip`） | openssl 付きで再ビルドしたことで、SRT と同一バイナリで両立できた（F-5） |
| 常駐 | launchd（将来：systemd） | Docker常駐でMac miniのメモリを食わない |

### 単一出力に絞ったことの設計上の効果

複数出力を捨てたことで、次の複雑さがまるごと消える。**この単純さを守ることを設計の制約とする。**

| 消えたもの | 理由 |
|---|---|
| `tee` muxer 構成 | 出力が1つなので分配が要らない |
| 共有エンコード／個別エンコードのモード切替 | 常に1エンコード1出力 |
| 出力ごとのオーバーレイ出し分け | プロトコル名は常に1つ。無条件で焼き込める |
| 上り帯域の合計管理・並列本数の上限計算 | 1本分だけ見ればよい |
| ジョブの同時実行管理 | **同時稼働は1ジョブに限定**。2本目の開始時は「停止して差し替えますか」と聞く |

## 2. データモデル

```
Target（送出先）
  id, name, raw_url（貼られた原文）, protocol[rtmp|srt|whip], detected_by[auto|manual]
  parsed(JSON)  … プロトコル別の分解結果
    ├ rtmp: base_url, stream_key
    ├ srt:  host, port, streamid, latency_ms, passphrase(暗号化), pbkeylen, mode
    └ whip: endpoint_url, bearer_token(暗号化)
  last_used_at, use_count

Template（エンコード条件）★自動保存
  id, name, is_builtin, is_pinned, is_auto_named
  settings_hash（内容の正規化ハッシュ／重複排除キー）
  settings(JSON)
    video: codec[h264|hevc], encoder[libx264|h264_videotoolbox],
           width, height, fps, bitrate_kbps, maxrate, bufsize,
           gop_sec, bframes, preset, profile, tune
    audio: codec[aac|opus], bitrate_kbps, samplerate, channels
  created_at, last_used_at, use_count

Source（映像ソース）
  id, name, type[file|live_url|testsrc]
  ├ file:     path, loop(bool)
  ├ live_url: url, reconnect(bool)
  └ testsrc:  pattern[smptebars|testsrc2], with_tone(bool)
  last_used_at

Overlay（焼き込み設定）※ジョブ単位
  clock_enabled, clock_mode[wallclock|framecount|both], clock_position, clock_size
  info_enabled, info_items[], info_position

Job（実行単位）※同時に running は最大1件
  id, target_id, template_id, source_id, overlay(JSON)
  duration_sec(null=無期限), auto_restart(bool)
  status[running|stopped|failed], pid, pgid, started_at, ended_at,
  resolved_command, exit_code, restart_count, last_error
```

**設計上の要点**：`Job.resolved_command` を必ず保存する。「あのときの設定」の完全な再現手段になり、UIから手元にコピーしてターミナルで単発実行することもできる。

## 3. 機能一覧

### F-1. 送出先の登録 ★URL自動判定

**URLを1つ貼るだけ。プロトコルは聞かない。**（憲章 Principle 1）

#### 判定ルール

| URLスキーム | 判定 | 根拠 |
|---|---|---|
| `rtmp://` `rtmps://` | **RTMP** | 一意 |
| `srt://` | **SRT** | 一意 |
| `http://` `https://` | **WHIP** | 本ツールの出力先として HTTP(S) を使うのはWHIPだけ。パスに `/whip` が無ければ警告、`http://` なら DTLS の都合で警告を出す |
| `rtsp://` `udp://` `rtp://` | **非対応** | 「現在このプロトコルは対応していません」と明示する。黙って失敗させない |
| スキームなし（`host:port` 等） | **判定不能** | プロトコル選択を明示的に聞く（このときだけ人に選ばせる） |

#### 判定と同時にパラメータを分解する

貼られたURLから、プロトコル固有の値を抜き出して個別フィールドに展開する。ここが**設定工数削減の主要な打ち手**。

```
srt://ingest.example.com:9000?streamid=publish/live/abc&latency=200&passphrase=secret
        ↓ 自動分解
  ホスト   : ingest.example.com
  ポート   : 9000
  streamid : publish/live/abc
  latency  : 200 ms
  passphrase : ●●●●●●（マスク表示）
```

RTMPは `rtmp://host/app/streamkey` の末尾セグメントをストリームキー候補として切り出す。ただし**切り出しは提案にとどめ**、実際の送出は原文URLをそのまま渡す（分解が間違っていても送出は壊れない構造にする）。

#### 分解時に出す警告（実装で判明した罠）

| 検出 | 警告内容 |
|---|---|
| **`latency` が 10000 未満** | **FFmpeg の SRT `latency` はマイクロ秒**。Haivision系のドキュメントや他ツールのUIはミリ秒で書かれているため、`latency=200` を貼ると 0.2ms になる。「200ミリ秒のつもりなら latency=200000 です」と具体値で示す |
| `passphrase` あり・`pbkeylen` なし | FFmpegの既定は16(AES-128)。配信先が256bitを要求するなら `pbkeylen=32` が要る |
| `mode` が caller 以外 | 本ツールは送出側（caller）前提 |
| SRTでポートなし | SRTはポート必須 |
| RTMPで末尾セグメントが1つだけ | ストリームキーが付いていない可能性 |
| **クエリに空の項目**（`&&` や末尾の `&`） | FFmpegは `Query string option '' does not exist` として**接続を試みる前に**失敗する。修正済みURLを提案し、ワンクリックで差し替えられるようにする |

#### クエリの分解に `parse_qsl` を使わない理由

標準の `urllib.parse.parse_qsl` は、この用途では2つとも致命的な副作用を持つ。

| 問題 | 何が起きるか |
|---|---|
| **`+` を空白に変換する** | FFmpeg が SRT オプションを取り出す `av_find_info_tag` は URL デコードを一切しない。`streamid=a+b` はそのまま `a+b` として libsrt に渡る。`parse_qsl` で表示すると「a b」に見え、**実際に送られる値と表示が食い違う** |
| **空のセグメントを黙って捨てる** | `a=1&&b=2` の `&&` は表示から消える。しかしFFmpegは空のオプション名として扱い、接続前に失敗する。**画面を見ても原因が分からない**状態になる |

どちらも実際に踏んだ。Ceeblue への送出が `Option not found` で失敗し、UI 上は
streamid の `+` が空白に見えていたため、原因が `+` にあるように見えていた。
実際の原因は `&&` で、`+` は無関係だった（`app/protocol.py` の `parse_query`）。

**表示は「FFmpegが受け取るのと同じ文字列」でなければならない。** 見やすさのための
デコードが、切り分けを遠回りにする。

`latency` の単位は実務で確実に刺さる。ここを黙って通すと「繋がるのに映像が壊れる」という
最も切り分けづらい症状になるため、判定と同時に警告する価値が高い。

#### 秘匿値の扱い

配信先URLには**ストリームキーや passphrase が丸ごと含まれる**。したがって:

| 対象 | 扱い |
|---|---|
| 保存 | URLを丸ごと暗号化（Fernet）して `targets.url_enc` に格納。鍵は `data_dir/secret.key`（0600） |
| 表示・履歴 | 秘匿値を `●●●●●●` に置換した `display_url` のみ |
| `resolved_command` | 伏せ字版を保存する。**コピーしてそのまま実行はできない**が、画面共有やスクショでの流出を防ぐ方を優先した |
| 伏せ字の方式 | **URL全体を伏せ字版URLに置換**するのが基本。完全一致なので巻き添えが出ない。自由文中の個別の秘匿値は8文字以上のものだけ置換する（短い値を無差別に置換すると `drawtext` が `drawte●●●t` になる事故を実際に踏んだ） |
| FFmpegのログ | 出力行ごとに伏せ字を適用してから保存・配信する |
| 再送出 | UIは `target_id` だけを送る。平文URLがブラウザ側に戻らない |

守れる範囲は限定的である点も明記しておく。鍵は同じマシンの同じユーザーから読めるので、
これは「DBやバックアップが持ち出されたときの被害を減らす」措置であって、アクセス制御ではない。

#### 誤判定への備え

判定結果は**必ずバッジで表示**し、その横に「変更」を置く。手動で変えた場合は `detected_by = manual` として記録し、以後同じURLでは学習した判定を優先する。

> **なぜここまでやるか**：自動判定の価値は工程を1つ減らすことだが、黙って間違えると切り分けに30分溶ける。「自動で決める」と「決めた理由が見える」はセットで初めて成立する。

#### 疎通確認

保存前に「疎通確認」ボタン。数秒だけ最小構成（testsrc・低ビットレート）で送出し、成否だけを返す。

##### SRT の失敗を3つに分ける

FFmpeg は原因が何であれ `Input/output error` としか言わない。しかし**やるべきことは正反対**になるので、機械的に分ける。

| 状態 | 判定方法 | 出す説明 |
|---|---|---|
| **一度も繋がっていない** | ログに `Connection to srt://... failed` | SRTの induction ハンドシェイクを1発投げ、応答の有無を確かめる（下記） |
| **繋がったが送出中に切断** | ログに `Error submitting a packet` 等 | 経路は問題ない。同一 streamid の重複配信・同時接続数・権限を疑う |
| 成功 | exit 0 | — |

##### induction ハンドシェイクによる到達性判定（`app/srtprobe.py`）

SRTのハンドシェイクは2段階で、**1段目（induction）は streamid を送る前**に行われる。
したがって induction に応答があるかどうかは、認証情報と無関係に
「そこに SRT サーバーが居るか」だけを教えてくれる。

| 結果 | 意味 | 次にやること |
|---|---|---|
| 応答あり | SRTサーバーは居る | streamid / passphrase / 権限を疑う |
| 無応答 | サーバーが居ないか経路が塞がれている | **streamid をいじっても無駄**。ポート番号・UDP経路・ingestの有効化を確認 |
| ICMP到達不能 | ホストには届くが、そのポートは待ち受けていない | ポート番号が違う |

> **なぜ作ったか**：実際にこれで時間を溶かした。Ceeblue への送出が `Input/output error` で
> 失敗し、streamid の形式（`+` や `,t=`）を疑って調査が長引いた。induction を投げてみると
> **指定ポートは無応答、別のポートは46msで応答**しており、原因は streamid ではなく
> ポート番号だった。この判定が最初からあれば一発で分かる。

### F-2. ソース管理（映像ソース）

| type | 内容 | FFmpeg入力 |
|---|---|---|
| `testsrc` | 内蔵テストパターン（ファイル不要・**既定**） | `-re -f lavfi -i testsrc2=...` + `sine` |
| `file` | ローカルに置いたファイルをループ | `-stream_loop -1 -re -i /path/xxx.mp4` |
| `live_url` | 公開ライブソースを取り込み | `-re -reconnect 1 -reconnect_streamed 1 -i <url>` |

**ループの継ぎ目対策**：`-stream_loop -1` はループ境界でPTSが不連続になりやすい。出力前に `setpts=N/FRAME_RATE/TB`（映像）と `asetpts=N/SR/TB`（音声）を挟んでタイムスタンプを張り直す。ここを外すと長時間試験で必ず崩れる。

#### 継ぎ目の「約200msの停止」と、その回避

タイムスタンプを直しても、**`-stream_loop` は継ぎ目で入力を開き直すため出力自体が止まる**。
実測すると、ループのたびに約210msのあいだ1バイトも出ていない。

```
3.4s:215ms  7.1s:210ms  10.8s:210ms   ← 素材長3.7秒の継ぎ目と一致
```

下流はこの間バッファが枯渇し、**映像と音声が同時に一瞬乱れる**。
「映像だけ」でなく両方が乱れるのが、キーフレーム由来の問題と区別する手がかりになる。

入力側の小細工（`-noaccurate_seek`、`+genpts`、コンテナ変更）はいずれも効かなかった。
効いたのは **`loop` / `aloop` フィルタでデコード済みフレームをメモリに抱える**方法で、
入力を開き直さないので停止が消える（実測 3回 → **0回**）。

| 方式 | 継ぎ目の停止 | メモリ |
|---|---|---|
| `-stream_loop -1`（従来） | 3回 / 最大215ms | 170MB |
| `loop` フィルタ | **0回** | 304MB |

メモリと引き換えなので、**素材が短いときだけ**自動で切り替える
（`resolve_seam()`、既定の上限は約900MB相当）。長い素材は従来方式に落とし、
「継ぎ目で約200msの途切れが出ます」と伝える。手動指定も可能。

**外部ライブソースの扱い**：
- 既定のカタログは**テスト用途で公開されているストリーム**だけを同梱する
- 放送局の linear チャンネルなど再送出の権利関係が曖昧なものは含めない（Public化に伴い、個人検証用に入れていた Red Bull TV を削除した）。`caution` フラグと UI の ⚠ 表示は、そういうものを個人用に足す場合に備えて残してある
- 任意URLは「上級者オプション」として、規約確認は利用者責任である旨をUIに明記
- YouTube等のプラットフォームからの取得機能は**同梱しない**

#### カタログの構成（2026-09-13 時点・全件 ffprobe で到達確認済み）

用途が違うので、UI でも2グループに分けて見せる。

| 区分 | 用途 | 収録 |
|---|---|---|
| **24時間ライブ** | 長時間の耐久試験、再接続の検証 | Unified Streaming ライブ / 同 SCTE-35入り / Shaka Player ライブ / Mux 低遅延HLS |
| **VOD** | 毎回同じ内容が流れるので、再現性のある比較に向く | Big Buck Bunny / Apple BipBop / Tears of Steel |

外部サービスなので落ちることはある。カタログは**当たりを引くための出発点**であって、可用性を保証するものではない。

#### HLSマスタープレイリストは、こちらでバリアントを選ぶ

**FFmpeg にマスターを渡してはいけない。** 実測で2つの実害が出た。

| 症状 | 原因 | 実測 |
|---|---|---|
| 画質が著しく低下する | `-map 0:v:0` が**先頭のバリアント＝最低画質**を掴む。それを目的の解像度に拡大するので崩れる | 224x100 を 1280x720 に拡大していた |
| 稼働開始までタイムラグ | 全バリアントを開きにいく | **23.5秒** → バリアント直指定で **4.3秒** |

対応：`sources.pick_variant()` で**目的の高さ以上のうち最も小さいバリアント**を選び、
そのURLを FFmpeg に渡す。無ければ一番大きいものを使う（拡大は避け、無駄な縮小もしない）。
選んだ結果は画面に出す。

#### 素材の先読みは、遅延測定と両立する（バッファの位置の問題）

「たまに止まる」対策として素材を数秒貯めたい。これは遅延測定と衝突しない。
**焼き込む時計は `drawtext` を通る時点の壁時計**なので、バッファが焼き込みより
**手前**にある限り、測る遅延には一切乗らないため。

| バッファの位置 | 効果 | 測定遅延 |
|---|---|---|
| 焼き込みより**手前**（入力側） | 素材の詰まりを吸収できる | **影響なし** ✅ |
| 焼き込みより**後ろ**（送出側 / `-readrate_initial_burst`） | 下流に積み上がるだけ | **そのぶん増える** ❌ |

##### 入力側バッファの作り方

ライブHLSは既定でライブ端の3セグメント手前から読み始めるが、**速度制限が無いと
すぐ端に追いついて余裕が消える**。手前から読み始めたうえで1倍速に保つと、
その差がそのまま素材の貯金になる。

| オプション | 役割 |
|---|---|
| `-live_start_index -N` | ライブ端の N セグメント手前から読む。N は `#EXT-X-TARGETDURATION` から秒数を割って求める |
| `-readrate 1` | 1倍速に保つ。これが無いと端に追いついて貯金が消える |
| `-readrate_catchup 1.5` | 遅れたときだけ速く読んで取り戻す。先行しない |
| `-readrate_initial_burst` | **使わない**。読んだぶんをそのまま送り出すので、測定遅延が増える |

##### 実測

ローカルにライブHLSを立て、途中で供給を止めて出力が何秒続くかを測った。

| 設定 | 供給停止後に出し続けた時間 | 入力側の貯金 |
|---|---|---|
| 既定（ライブ端で読む） | **0.1秒** | 3秒 |
| `-readrate 1` + 端から-10 | **10.5秒** | 11秒 |

貯金の深さは、素材側にも時計を焼いて出力の時計と比べることで直接測った
（素材 02:04:55 / 出力 02:05:06 → 11秒）。

#### 実時間に絞るのは `realtime` フィルタで行う（`-re` は使わない）

**`-re` は、映像と音声の両方を符号化すると間欠的に壊れる。** 実測で判明した。

処理能力が10.9倍余っているのに、実時間の 0.81〜0.83 倍へ落ちた状態に嵌まる。
同一条件6回で `0.812 / 0.950 / 0.812 / 1.004 / 1.004 / 1.002` という
**バイモーダル**な出方をする（0.83 は 50fps 相当で、スリープ粒度が 20ms に
粗くなった形に見える）。

切り分けの結果は次のとおり。

| 構成 | 定常レート |
|---|---|
| `-c copy`（デコードなし） | 1.000 |
| 映像のみ符号化 | 1.000 |
| 映像符号化 + 音声 copy | 1.000 |
| 映像 copy + 音声符号化 | 1.020 |
| **映像 + 音声を両方符号化** | **0.81〜0.87（間欠）** |
| ペーシング無し（上限） | 10.85 |

ビットレート・プリセット・キューサイズ・`taskpolicy` のいずれでも安定しなかった。

**`realtime` / `arealtime` フィルタに替えると安定する。** フィルタグラフの中で
待つ方式で、同条件5回すべて 0.99〜1.01。実機でも fps 47.8 → 59.3、
平滑化レート平均 1.000（0.95未満は30サンプル中0件）に改善した。

| ソース | 絞り方 |
|---|---|
| testsrc / file / VOD の live_url | **`realtime` + `arealtime` フィルタ** |
| 本物のライブ（`pace=asfast`） | 絞らない。入力がすでに実時間で来ている |
| `-c copy`（Passthrough） | フィルタを通らないので、そこだけ `-re` |

**`realtime` はオーバーレイより前に置く。** 待ってから時計を焼くので、
焼いた時刻と送出時刻がずれない。

##### 旧記述（`-re` 前提）は上記に置き換えた

実装で最も間違えやすかった点。

| ソース | `-re` | 理由 |
|---|:---:|---|
| testsrc / file | **付ける** | 付けないと全力で生成・デコードし、送出先にバースト送信してしまう |
| live_url | **付けない** | 入力がすでに実時間で流れてくる。さらに絞ると二重に待つことになりバッファが溜まる |

#### 入力の健全性監視 — 実装した範囲と、していない範囲

当初の設計は「入力断を検知したら `testsrc` の SOURCE LOST パターンに自動フォールバックし、送出自体は維持する」だった。**これは実装していない。**

| 手段 | 実装 | 備考 |
|---|:---:|---|
| HTTP入力の再接続（`-reconnect`） | ✅ | FFmpeg 自身が繋ぎ直すのでプロセスは生き続ける。**HTTP(S) 固有のオプション**で、rtmp:// や srt:// の入力には効かない |
| プロセスごとの自動再接続 | ✅ | 落ちたら指数バックオフで立て直す（下記） |
| 無停止での SOURCE LOST 差し替え | ❌ | 1本の FFmpeg プロセスの中で入力を切り替えるには `streamselect` + `zmq` などの外部制御が要る。libzmq への依存と、フィルタグラフの複雑化に見合わないと判断した |

「送出が途切れない」ことを本当に保証するなら、ローカルに中継を1段挟む構成（FFmpeg → ローカル中継 → 送出先）が要る。必要になった時点で別途設計する。

**外部ライブソースは http(s) のみ受け付ける。** 自動再接続がHTTP固有の機能である以上、他プロトコルを受け付けると「再接続するつもりでしない」状態になるため、入口で断っている。

**ファイルの置き場所**：`~/StreamForge/media/`（設定ファイルで変更可）。Web UIからアップロードもできるが、Finderで直接置いたファイルも一覧に出る。母艦がMacであることの利点を使う。

### F-3. エンコード設定とテンプレート自動保存 ★

#### 既定値（何も触らずに送出できる状態）

| 項目 | 既定値 |
|---|---|
| 解像度 / fps | 1920x1080 / 30 |
| 映像コーデック | H.264（`libx264`） |
| ビットレート | 4500 kbps（maxrate 4500k / bufsize 9000k） |
| GOP | 2秒（`-g 60 -sc_threshold 0`） |
| preset / bframes | `veryfast` / 2 |
| 音声 | AAC 128kbps / 48kHz / stereo |

#### ビルトインテンプレート（削除不可）

| 名称 | 内容 | 用途 |
|---|---|---|
| Standard 1080p30 | 上記既定値 | 標準的な疎通確認（**初期選択**） |
| Low 720p30 | 1280x720/30, 2500k, GOP 2s | 負荷を抑えたい／回線が細いとき |
| LowLatency 720p30 | 1280x720/30, 2500k, GOP 1s, `ultrafast` + `tune=zerolatency` + `bf 0` | 遅延を見るとき（条件を固定するためのプリセット） |
| High 1080p60 | 1920x1080/60, 6000k | 高負荷・帯域試験 |
| WebRTC互換 720p30 | 1280x720/30, 2500k, GOP 1s, `bf 0`, `profile baseline` | **配信先がWebRTCで配信する場合**（Ceeblue等）。下記参照 |
| Passthrough | `-c copy` | エンコードせず疎通だけ見る。**テストパターンとは併用できない**（入力をそのまま流すため、P4のファイル／外部ライブソースが要る）。オーバーレイも使えない |

#### テンプレート自動保存の仕組み

**名前を付けて保存する作業を、ユーザーから完全に取り除く。**（憲章 Principle 2）

```
送出開始ボタンを押した時点で:
  1. エンコード設定を正規化（キー順ソート、既定値の補完）→ SHA-256 で settings_hash を算出
  2. 同じ hash のテンプレートを検索
       ├ 見つかった → last_used_at を更新、use_count++ （新規保存はしない）
       └ 見つからない → 新規テンプレートとして自動保存
            name = 自動生成（例: "1080p30 · 6000k · H.264 · GOP1s"）
            is_auto_named = true
  3. Job にその template_id を紐付けて起動
```

| 論点 | 決定 | 理由 |
|---|---|---|
| いつ保存するか | **送出開始時**（設定を触った瞬間ではない） | 触っただけの中間状態がゴミとして残るのを防ぐ。「実際に使った設定」だけが残る |
| 重複をどう防ぐか | 内容ハッシュで同一判定 | 同じ設定を何度使ってもテンプレートは1件。使用回数だけが増える |
| 名前 | 自動生成。UIでインラインリネーム可（するとピン留め扱い相当で保護） | 名付けを強制しない。でも名付けたくなったらできる |
| 増えすぎたら | 非ピン・非ビルトインを最終使用日でLRU整理し、**30件**を超えたら古い順に削除 | 自動保存の副作用（一覧が汚れる）を自動で回収する |
| 一覧の並び | ①ピン留め ②最近使った順。使用回数もバッジ表示 | 「別の機会に選べる」を実効性のあるものにする |

#### 実装時に決めた細部

| 論点 | 決定 | 理由 |
|---|---|---|
| 正規化の範囲 | `maxrate`/`bufsize` の未指定は既定値に埋めてからハッシュする | 「4500k / maxrate未指定」と「4500k / maxrate 4500k」は同じ設定。埋めないと同一内容で2件できる |
| Passthrough の正規化 | `{"mode": "passthrough"}` だけを見る | 再エンコードしないので解像度やビットレートは意味を持たない。値が違っても同じテンプレート |
| ビルトインとの衝突 | 利用者の自動保存テンプレートがビルトインと同じ内容なら、その行を**ビルトインに昇格**させる | 同じ設定の行が2つできるのを防ぐ。使用回数も引き継がれる |
| 並び順の同着 | `last_used_at` は秒精度なので、`id DESC` を第2キーに置く | 連続で送出すると同一秒になり、「最後に使ったもの」が不定になる |
| リネームの副作用 | 名付けたら `is_auto_named=0` にし、LRU整理の対象から外す | 名前を付けた＝利用者が意思を示した、とみなす。ピン留めと同じ保護 |
| ピン留めと自動命名 | ピン留めは自動命名のままでも保護される | 名付けずに「これは残す」と言えるようにする |

#### 前回設定の復元

新規ジョブ画面を開いたとき、**最後に使ったテンプレート・ソース・送出先**が初期選択された状態にする。連続でテストするときは本当に「開始」だけになる。

UIでフォームを手で触ると、テンプレート選択は自動的に「カスタム」に戻る。「選んだつもりの設定」と「実際に送る設定」がずれないようにするため。

#### Macでのハードウェアエンコード

`h264_videotoolbox` を選択肢として持つ（Mac mini M4 のメディアエンジンを使い、CPUを空ける）。ただし：

- **既定は `libx264`** にする。VideoToolboxは画質・レート制御の挙動がlibx264と異なり、Linux移植時に同じ結果が出ない
- **`-a53cc 0` を必ず付ける。** 入力に A53 クローズドキャプションが載っていると、VideoToolbox はそれを SEI として出力に載せ直そうとして落ちる（`Unexpected end of SEI NAL Unit parsing type` → `Error copying packet data`）。Apple BipBop で再現した。libx264 は同じ入力でも問題ないので、そちらは既定のまま。本ツールはエンコードの試験が目的でCCの再現は目的ではない
- テンプレートに `encoder` を保持し、Linux環境で `h264_videotoolbox` のテンプレートを開いたら自動的に `libx264` へ読み替えて警告を出す（憲章 Principle 6）

### F-4. オーバーレイ（時計・設定焼き込み）★差別化機能

#### F-4-1. 時計オーバーレイ

3つのモードを持つ。**用途によって必要な精度が違う**ため。

| モード | 表示内容 | 精度 | 用途 |
|---|---|---|---|
| `wallclock` | `2026-09-12 14:33:07.482` | 秒はサーバー壁時計、ミリ秒はPTS由来。秒境界で最大1フレームのズレ | 受信端末の時計と見比べる**絶対遅延**の概算 |
| `framecount` | `F:0000123456` | 完全に正確 | 別プロトコルで送り直したときの**相対比較**、フレーム落ちの検出 |
| `both` | 上下2段 | — | **既定** |

FFmpeg フィルタ（例）：

```
drawtext=fontfile=<repo>/assets/fonts/DejaVuSansMono-Bold.ttf:
  text='%{localtime\:%H\\\:%M\\\:%S}.%{eif\:trunc(mod(t\,1)*1000)\:d\:3}':
  x=(w-tw)/2:y=h*0.08:fontsize=h/16:fontcolor=white:
  box=1:boxcolor=black@0.6:boxborderw=10
```

> **なぜこの式か**：`%{localtime}` は秒までしか出せない。ミリ秒は `t`（フレームのタイムスタンプ）の小数部から作る。`-re` で実時間読みしているので両者はほぼ一致するが、秒の桁上がりの瞬間だけ最大1フレーム分ズレうる。厳密な比較には `framecount` を使う、という役割分担にしている。

> **フォントをリポジトリに同梱する理由**：macOSとLinuxでシステムフォントのパスが違う。同梱すれば `drawtext` の指定が両OSで同一になり、見た目も揃う。移植コストを設計時点で潰しておく。

**時刻同期の前提**：Mac miniのNTP同期状態（`sntp` / `systemsetup -getusingnetworktime`）を起動時に確認し、UIに表示する。同期していなければ `wallclock` モードに警告を出す。

#### F-4-2. エンコード設定の焼き込み

送出中のパラメータをそのまま画面に載せる。**受信側のスクショ1枚で条件が確定する**ことが目的。単一出力なので、プロトコル名も無条件で焼ける。

```
┌─────────────────────────────────┐
│         14:33:07.482            │  ← 時計
│         F:0000123456            │
│                                 │
│                                 │
│ SRT | 1920x1080@30 | H.264      │  ← 設定情報（左下）
│ 4500k | GOP 2.0s | veryfast     │
│ job#42 ceeblue-tokyo            │
└─────────────────────────────────┘
```

表示項目はチェックボックスで選択可。文字列はCommand Builderが**テンプレート値から自動生成**するため手入力は不要。実際の設定と表示が乖離しない。

### F-5. WebRTC（WHIP）送出 ✅

#### 実現までの経緯

当初、手元の FFmpeg に WHIP muxer が無く「SRT・WHIP・drawtext を同時に満たすビルドが存在しない」として第2段階に送っていた。原因は `--enable-openssl` の不在で、WHIP muxer が DTLS-SRTP のために TLS ライブラリを要求するため。

`--with-openssl@3` 付きで tap 版を再ビルドしたところ **1分18秒で完了し、1バイナリで全機能が揃った**（FFmpeg 9.0.1）。見積もりが過大だったため、P5 より前倒しで実装した。

#### 実装

| 項目 | 内容 |
|---|---|
| 出力 | `-f whip <エンドポイントURL>` |
| 認証 | `-authorization <Bearerトークン>`。**URLには載せない** |
| ハンドシェイク | `-handshake_timeout 10000`（既定5秒は遠いリージョン相手だと短い） |
| トークンの保存 | `targets.secret_enc` に URL とは別に暗号化して格納。表示は有無だけ |

#### WebRTC で配信される場合の制約（送出プロトコルによらない）

**症状**：SRT で送ると音声は正常なのに、映像だけ真っ暗になる。

**原因**：WebRTC CDN（Ceeblue 等）は受け取った映像を再エンコードせずに WebRTC へ流す。
ブラウザは H.264 を **constrained baseline**（`profile-level-id=42e01f`）でネゴシエートし、
**Bフレームを運べない**。既定設定（`profile high` + `bf 2`）で送ると、実際には Main profile /
Bフレーム63%のストリームになり、ブラウザがデコードできず黒画になる。音声は別コーデックで
CDN側が変換するため正常に聞こえ、**映像だけ壊れているように見える**のが厄介なところ。

実測（1280x720/30, 3秒）：

| 設定 | 実際に出るprofile | Bフレーム |
|---|---|---|
| `ultrafast` + `profile high` + `bf 2`（既定） | Main | 57 / 90 枚 |
| `bf 0` を足す | **Constrained Baseline** | 0 |
| `veryfast` + `profile baseline` + `bf 0` | **Constrained Baseline** | 0 |

**対応**：ジョブに「配信先がWebRTCで配信する」チェックを設けた。入れると
Bフレーム無効・baseline に落とし、**何を変えたかを画面に出す**。
ビルトインの「WebRTC互換 720p30」でも同じ状態になる。

**音声は触らない。** SRT は MPEG-TS で AAC を運び、Opus への変換は配信先が行う。
ここで Opus にすると逆に運べなくなる（WHIP で自分が WebRTC 送信者になる場合だけ Opus にする）。

#### プロトコル制約の自動読み替え

WebRTC には RTP で運ぶがゆえの制約がある。**黙って直さず、何を変えたかを UI に出す**（憲章 Principle 1）。

| 条件 | 読み替え | 理由 |
|---|---|---|
| 音声が AAC | → Opus | WebRTC は Opus 必須 |
| 音声が3ch以上 / 48kHz以外 | → 2ch / 48kHz | WebRTC の Opus の制約 |
| Bフレームあり | → `bf=0` | RTP の H.264 パケット化が B フレームを扱えない |
| GOP が2秒超 | → 2秒 | 受信側が映像を出し始めるまでを短くする |
| プロファイルが high | → main | 受信側の互換性 |

読み替えは**コマンド生成時にのみ適用**する。テンプレートに保存されるのは利用者が指定した元の設定で、WHIP用に変形したものが勝手にテンプレート化されることはない。

#### 検証で判明した制約：ICE 候補を1つしか試さない

ローカルの mediamtx 相手に DTLS ハンドシェイクが 5 秒でタイムアウトする現象が出た。debug ログを見ると、FFmpeg が **Tailscale の IPv6 アドレス**（`fd7a:115c:a1e0::/48`）を掴んでいた。

**FFmpeg の WHIP muxer は完全な ICE を実装しておらず、サーバーが広告した候補のうち1つを選んで終わり**。到達できない候補を引くとそのまま失敗する。

- 公開CDN（グローバルIPを1つ広告）相手では問題になりにくい
- **自前・社内のWHIPサーバー相手では、サーバー側の候補広告設定が効いてくる**
- 繋がらないときは、まずサーバーが広告している候補を疑う

ローカル検証の手順（mediamtx の設定込み）は `環境検証メモ.md` に記載した。

### F-6. ジョブ実行・監視

#### 単一ジョブ制約

同時に `running` なジョブは**1件のみ**。稼働中に新規開始しようとしたら「現在のジョブを停止して差し替えますか？」を出す。並列を意図的に禁じることでリソース管理も帯域管理も不要になる。

##### 踏んだバグ：チェックと状態設定のあいだに await があった

`start()` はプロセス生成で `await` する。当初はその**後**に「稼働中」フラグを立てていたため、
チェックを通った2本目がその隙間に入り込み、**両方が起動した**。

```
16:36:09  ジョブ#76 開始      ← 1秒差で2本
16:36:10  ジョブ#77 開始
16:36:13  #76 が終了 → 共有状態をクリア
          → #77 のプロセスは生きているのに running_job_id が None になり、
            UIからは停止したように見え、止める手段も無くなる
```

さらに `_finalize()` が**どのジョブの終了かを見ずに**共有状態を落としていたため、
先に終わった側が生きている側の追跡情報を消していた。

対策は2つ。

| 対策 | 内容 |
|---|---|
| 隙間をなくす | `await` より**前**に稼働中フラグを立てる。起動に失敗したら戻す |
| 直列化する | `asyncio.Lock` で `start()` 全体を囲む（二重の保険） |
| 巻き添えを防ぐ | `_finalize()` は自分が追跡しているジョブのときだけ共有状態に触る。別ジョブならDBだけ更新する |

再発防止のため、実際に並行 `start()` を投げる回帰テストを置いた。
修正を外すと `2本起動してしまった` で落ちることを確認済み。

> ブラウザのタブを2つ開いていると、サーバー側の制約だけが最後の砦になる。
> UIのボタン無効化はタブをまたげない。

#### 起動と停止

- `setsid` でプロセスグループを作って起動し、停止時は**プロセスグループごと** SIGTERM → 5秒後 SIGKILL。FFmpegの子プロセス残留を防ぐ
- DBには `pid` と `pgid` の両方を保存
- **API起動時の整合処理**：DBで `running` のジョブについて実プロセスの存在を確認し、無ければ `failed(orphaned)` に落とす（憲章 Principle 4）

#### 自動再接続

- 異常終了を検知 → 指数バックオフ（2s, 4s, 8s, 最大60s）で再起動
- 再起動回数をジョブに記録し、UIに「再接続 3回」と表示する。**静かに直さない**（これは障害の証拠になる）
- 1時間あたり10回を超えたら再起動を止めて `failed` にする

#### タイムアウト

既定2時間。UIで「無期限」を選べるが、その場合は一覧で目立つ色を付ける。Mac miniは常時稼働なので、消し忘れが実害になる。

#### ログ

FFmpegのstderrを2系統に分ける。

| 系統 | 内容 | UI |
|---|---|---|
| 進捗 | `-progress pipe:1` の構造化出力（fps, bitrate, speed, drop_frames） | 数値パネルとスパークラインで毎秒更新 |
| メッセージ | stderrの警告・エラー | 生ログ（末尾5MB）＋**翻訳済みエラー**を上部に表示 |

#### 順調なときこそ無言になる問題

FFmpeg は正常に流れているあいだ何も出力しない。その結果、ログ欄が空のままになり
「本当に動いているのか」が分からなくなる（実際にそう指摘された）。

**60秒ごとに稼働状況を1行流す。** 数字は上のパネルにも出ているが、
**時刻付きで履歴に残る**ことに意味がある（後から見返せる）。

```
[streamforge] 送出中 — 経過 1:02:05 / fps 30.0 / bitrate 2500k / speed 1.00x / drop 0 / 残り 57分
```

再接続が起きていればその回数も添える。残り時間はタイムアウトが設定されている場合だけ。

#### テスト後に振り返るための記録（F-6 の一部）

送出中の指標は画面を閉じれば消え、指摘は発生時に1回しか流れない。
**後から「あのとき何が起きたか」を確認できないと、テストの意味が半減する。**

| 残すもの | 置き場所 | 備考 |
|---|---|---|
| 経時の指標（レート・fps・ビットレート・drop） | `job_samples` | 5秒間隔に間引く。2時間で約1440行 |
| 指摘の発生と解消 | `job_events` | 発生時刻つき |
| 生ログ | ログファイル | 全行。間引くのは画面表示だけ |
| 設定・コマンド・結果 | `jobs` | 既存 |

`GET /api/jobs/{id}/report` で1つのJSONにまとめて落とせる
（`log=full` / `log=none` で本文量を選べる）。**秘匿値はDBに入っている時点で
伏せ字済みのものだけを使う**ので、そのまま人に渡せる。

冒頭に `summary.verdict` として一言の結論を入れている。数字だけ渡されても
判断に時間がかかるため。

```
"verdict": "安定して送出できました（平均 1.00x）"
"verdict": "実時間に追いつけていない時間が 12% ありました（最低 0.71x）"
"verdict": "再接続が 3 回発生しました。安定していません"
```

> 実装で2つ踏んだ。`lines[-0:]` は全件を返すので「ログ不要」が効かない。
> また out_time が巻き戻ると（再接続や進捗の欠測）レートが**負**になり、
> 平均を壊すうえ `0 < speed` の判定をすり抜けて**警告まで止めていた**。

**エラー翻訳**（憲章 Principle 3 の実装）：`app/errors.py`。翻訳は**追加情報**として出し、生ログは常に併記する。翻訳が外れたときに元の手がかりが消えないようにするため。同じ指摘は1ジョブにつき1回だけ出す（再接続時にリセット）。

進捗の数値からしか分からない不調はログに出ないので、別経路で判定している（`app/errors.py` の `ProgressHealth`）。

##### speed の見方：一過性の落ち込みで警告を出さない

`-re` で実時間読みしている以上、**speed は 1.0 で頭打ちになる**。つまり揺らぎは必ず
下振れとして現れる。1サンプルの落ち込みで警告を出し、それを出しっぱなしにすると、
実際には正常に流れているのに「追いついていません」が画面に残り続ける。

実測した例（外部ライブソース、0.5秒刻み）：

```
1.64  0.822  1.11  1.67  1.72  1.75  2.02
      ↑ 一過性。ここで警告を出して残すのは誤り
```

そこで次の3点にした。

| ルール | 値 |
|---|---|
| 起動直後は見ない | 最初の4サンプル |
| 連続して遅いときだけ言う | 3サンプル連続 |
| 回復したら取り消す | `diagnosis` に `resolved` を付けてUIから消す |

`drop_frames` は累積値なので、**増分**を見て増えたときだけ言う。

##### GPU（VideoToolbox）は速くない — 実測

「重いならGPUを使えばいい」は、このマシンでは**逆効果**だった。

1080p60 / 8Mbps / オーバーレイあり（数値は実時間比。高いほど余裕がある）:

| エンコーダ | 実時間比 |
|---|---|
| libx264 `ultrafast` | **12.8x** |
| libx264 `superfast` | 8.6x |
| libx264 `veryfast` | 7.3x |
| libx264 `faster` | 4.9x |
| libx264 `medium` | 3.9x |
| **h264_videotoolbox** | **3.5x** |

VideoToolbox はオーバーレイの有無でも `-realtime` の指定でも 3.5x から動かない。
**エンコーダ自体の上限**（1080pで約210fps）で、フィルタ側の問題ではない。
デコードとフィルタは system memory 上で行われるため、フレームごとに
CPU↔GPU の転送も挟まる。

したがって扱いは次のとおり。

| 項目 | 判断 |
|---|---|
| 既定 | **libx264 のまま。** 速度でも品質でも VideoToolbox を選ぶ理由がない |
| 位置づけ | CPUを他の用途に空けたいときの選択肢として残す（オプション） |
| Linux移植 | 影響なし。能力検出に無ければ **libx264 へ自動で読み替えて通知する** |

##### 実例：speed 0.80x の原因はエンコードではなかった

稼働中のジョブを実況で見たところ、こうなっていた。

```
speed 0.80x（25秒間ずっと） / fps 47.7（目標60） / drop 0 / CPU 59.9%
```

**CPU が 60% しか使われていない。** エンコードが重いなら数百%に張り付くはずで、
この時点で「処理が重い」という見立ては外れている。同じ素材・同じ設定を
`-f null`（どこにも送らない）で回すと **7.27x** 出た。

犯人は送出側だった。上りの実測は次のとおり。

| | |
|---|---|
| 要求ビットレート | 8.1 Mbps（映像8000k + 音声128k） |
| 実際の上り（`netstat -ib` 実測） | **6.46 Mbps** |
| 比 | 6.46 ÷ 8.1 = **0.80** ← observed speed と一致 |

回線が要求ビットレートを出せず、その比率のぶんだけパイプライン全体が
引きずられていた。送出先は Wi-Fi 経由（`en1`）で、有線の口は空いていた。

**教訓：`speed < 1` は「エンコードが重い」を意味しない。** 対処が正反対になるので、
指摘の文面でも原因を決めつけず、切り分け手段（処理能力の計測）を案内する。

##### 「落ちるか」は測れるようにした

設定と機材の組み合わせ次第なので、目安を並べても外れる。
**同じパイプラインを5秒回して実時間比を測る**ボタンを付けた（`POST /api/jobs/benchmark`）。
出力は `-f null` に差し替えるので送出先には影響しない。

| 判定 | 意味 |
|---|---|
| 2.0x 以上 | 余裕あり |
| 1.2〜2.0x | 動くが余裕なし。他の負荷が乗ると落ちる |
| 1.2x 未満 | この設定では落ちる |

> 実装でひとつ踏んだ。出力指定を探すのに先頭から `-f` を走査すると、
> テストパターンの入力側にある `-f lavfi` に当たって入力ごと消える。
> `build_command()` は必ず `-f <muxer> <url>` で終わるので、**末尾の3つ**を落とす。

##### 参考：この機になっての実測能力（1080p素材 → 各設定、`-re` なし）

| 設定 | 実時間比 |
|---|---|
| LowLatency 720p30（ultrafast、オーバーレイあり） | **31.7x** |
| Standard 720p30（veryfast、オーバーレイあり） | 22.6x |
| VideoToolbox 720p30（オーバーレイあり） | 13.8x |
| High 1080p60（veryfast、オーバーレイあり） | 9.6x |

オーバーレイの追加コストは 3% 程度（31.7x → 32.7x）で、実質誤差。
**LowLatency が遅いということはあり得ない**ので、speed の落ち込みを見たら
CPU ではなく入力側（ネットワーク・ディスク）か一過性の揺らぎを疑う。

| 検出パターン | UIに出す文言 |
|---|---|
| `Connection to tcp://... failed` (RTMP) | RTMPサーバーに接続できません。URL・ポート（1935）・ファイアウォールを確認してください |
| SRT handshake タイムアウト | SRTのハンドシェイクが完了しませんでした。ホスト/ポート（UDP）とlatency設定を確認してください |
| `Encryption failed` / `KM REFUSED` | SRTのpassphraseが一致していません |
| WHIP `401` / `403` | WHIPエンドポイントの認証に失敗しました。Bearerトークンを確認してください |
| `speed=` が 0.9未満で継続 | エンコードが実時間に追いついていません。プリセットを下げるか VideoToolbox を試してください |
| `drop_frames` 増加 | フレームを落としています。上り帯域または送出先の受信能力を確認してください |

#### 「設定工数を極力減らす」ための具体策（このツールの本体）

1. **URLを貼るだけでプロトコルが決まる** — 選択の1工程を削除
2. **URL内のパラメータ自動分解** — streamid / latency / passphrase を手打ちしない
3. **既定値のまま送出できる** — 何も設定しなくても Standard 1080p30 で出る
4. **設定を変えたら自動でテンプレート化** — 保存操作なしで次回から選べる
5. **前回の選択を復元** — 連続テストは「開始」を押すだけ
6. **履歴からワンクリック再実行** — 過去の条件をそのまま再現
7. **コマンド書き出し** — 生成された ffmpeg コマンドをコピーでき、ターミナルやCIでも同じことができる

### F-8. セルフプレビュー ✅

送出中の絵を、送出側の画面で見る。設計の検討過程は `セルフプレビュー設計メモ.md`。

#### 何を見せ、何を見せないか

| 見せる | 見せない |
|---|---|
| エンコード直前（オーバーレイを焼いた後）のフレーム、毎秒1枚 | 受信側が実際に再生している絵 |
| その絵がいつのものか（更新からの経過秒） | 送出されたビットストリームそのもの |

受信側の確認は既存の analyzer の担当（憲章のスコープ表）。ここで肩代わりしない。
**混同されると危ないので、画面にも「受信側の絵ではありません」と書いてある。**

**セルフプレビューは静止画だけとする（2026-09-19 決定）。** 送出ビットストリームを
そのまま見る案（`tee` で分岐して LL-HLS）は検討したうえで見送った。送出と同じ
レートを食うので遠隔で見ると上り回線を奪い合ううえ、`tee` は**送出パスそのもの**を
差し替えるため、実インジェスト先での確認なしに入れる変更ではない。
必要な場面は稀（ビットストリームの健全性確認）で、そこは既存 analyzer で足りる。

#### 常時ONにできる理由

FFmpeg の引数は起動時に固定されるので、**途中でプレビューを足すには送出を切るしかない**。
「後から見たくなる」が普通に起きる以上、常時ONに倒せることが決定的に効く。
それができるのは、追加コストが誤差だと実測で分かっているため。

1080p60 / libx264 veryfast / 8000k / オーバーレイあり、10秒×3回の中央値：

| 構成 | 実時間比 | ベースライン比 |
|---|---|---|
| プレビューなし | 11.6x / 11.5x（前後2回） | — |
| JPEG 1fps 320px | 11.3x | −2% |
| **JPEG 1fps 480px（採用）** | 11.4x | **−1.5%** |
| tee → HLS（`-c copy`） | 11.5x | −0.9% |
| 別エンコード 640p15 | 11.0x | −5% |

帯域は 480px / 1fps で約 90kbps。**ここを軽くすることが本質**で、フルレートの
プレビューを Tailscale 越しに見ると、送出と同じ上り回線を奪い合う。
実際に踏んだ「上り 6.46Mbps に対して speed が 0.80x に張り付く」を、
プレビュー自身が引き起こしかねない（観測が対象を壊す）。

画面を裏に回している間はブラウザ側が取りに行かない。開いたまま放置されても
帯域を食い続けない。

#### 実装

```
-filter_complex "[0:v]<既存の映像フィルタ>,split=2[vout][snapsrc];
                 [snapsrc]fps=1,scale=480:-2[snap]"
-map [vout] … -f mpegts <送出先>            ← 送出（必ず先）
-map [snap] -c:v mjpeg -q:v 7 -update 1 -atomic_writing 1 -f image2 <data_dir>/snapshot/current.jpg
```

`-vf` から `-filter_complex` へ移したのは、出口を2つに分けるため。
分岐は**オーバーレイより後ろ**に置くので、プレビューに写るのは焼き込み済みの
フレームそのもので、絵からそのフレームの送出時刻まで読める。

| 決めごと | 理由 |
|---|---|
| **送出の出力を先、プレビューを後に置く** | `-progress` が報告するのは**最初の出力**の数字だけ。先に置くと監視が毎秒1枚の枝を見て、`video_rate` が 1/30 に見え「映像が出ていません」と誤報する（実際に出した） |
| `-t` は**両方の出力**に付ける | `-t` は出力ごとの指定。送出側だけに付けるとプレビュー枝が終わらず、lavfi 入力ではプロセスが一生終わらない |
| `-y` を付ける | `image2` は既存ファイルがあると `Overwrite? [y/N]` を聞いて止まる。`-nostdin` と組むと即死する |
| `-atomic_writing 1` | `-update 1` は同じファイルを切り詰めて書き直す。rename にしないと読み手が書きかけの JPEG を掴む |
| 置き場はジョブをまたいで1つ（`snapshot/current.jpg`） | コマンドを組む時点ではまだジョブIDが無い（IDは INSERT の戻り）。代わりに**起動時と終了時に消して**、前のジョブの絵を新しいジョブの絵として見ないようにする |
| passthrough では出さない | `-c copy` はフィルタを通らないので分岐する場所が無い |
| 計測（`/api/jobs/benchmark`）では付けない | 出力が2本になると `to_null_output()`（末尾3つが `-f <muxer> <url>` 前提）が壊れる。渡されたら **ValueError で落とす**（黙って間違えた数字を出さない） |

#### 副産物：映像停止の、数値とは独立した検出器

静止画の更新が止まる＝**フィルタを通った後の映像が出ていない**。
「音声だけ進み、`out_time` は 1.00x のまま映像が128秒止まる」は数値に出なかった事故で、
いまは `video_rate` が拾うが、**そのどちらも通り抜ける形**（書き出しの失敗など）が残る。

そこで、`fps` などの数値が正常なのに絵だけ15秒以上止まっている場合に指摘を出す
（`snapshot_stale`）。映像そのものが止まっているときは `slow_encode` が言うので、
**言うことを重ねない**。

#### この作業で見つけた既存バグ：処理能力の計測が常に 1.0 倍になっていた

`-re` から `realtime` フィルタへ移した時点（c393629）から、計測側の「絞りを外す」
処理（`-re` だけを見ていた）が効かなくなっていた。フィルタは残るので、
**どんな設定でも 0.8〜1.0 倍と出る**状態だった。

組み立て側に `pacing=False` を足し、計測用は最初から絞りを入れずに組むようにした。

| | 修正前 | 修正後 |
|---|---|---|
| 640x360@30 ultrafast | 0.83x（「この設定では処理落ちします」） | **124.0x** |
| 1920x1080@60 veryfast 8000k | — | **8.57x**（F-6 の実測 9.6x と整合） |

ffmpeg -hide_banner -protocols | grep -wE 'srt|rtmp' && ffmpeg -hide_banner -filters | grep -w drawtext

### 「いずれPublicにする」ための制約

後から機密を消す作業は履歴が残るぶん厄介なので、**最初のコミットから公開できる状態**を維持する。

| 守ること | 具体策 |
|---|---|
| 秘密情報をコミットしない | 送出先URL・ストリームキー・passphrase・Bearerトークンは**すべてDB（`.gitignore` 済み）** に置く。設定ファイルは `config.example.toml` だけをコミットする |
| 実データをコミットしない | `*.db` `media/` `logs/` `.env` を `.gitignore` に登録 |
| 社内固有情報を書かない | ドキュメントに顧客名・社内ホスト名・実インジェストURLを書かない。例示は `example.com` を使う |
| ライセンスを最初に決める | MIT。FFmpegはGPLビルドを使うが、本体はFFmpegを**外部プロセスとして呼ぶだけ**でリンクしないため、MITで配布できる |
| 公開前チェックリストを持つ | `公開前チェックリスト.md` に集約。公開時に上から潰す |
