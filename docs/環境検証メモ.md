# 環境検証メモ — Mac mini の FFmpeg 能力調査

実施日：2026-09-12
対象機：Mac mini M4 / macOS（Apple Silicon, arm64）
目的：StreamForge が必要とする **RTMP / SRT / WHIP / drawtext** が1つのFFmpegで賄えるかを確認する

---

## 結論（2026-09-13 更新：解決済み）

**解決した。** tap版を `--with-openssl@3` 付きで再ビルドしたところ、
**SRT・WHIP・drawtext がすべて揃った1バイナリ**になった（FFmpeg 9.0.1）。
所要時間は 1分18秒で、当初見積もった15〜30分より大幅に短かった。
これに伴い WebRTC(WHIP) を前倒しで実装した。

```bash
brew reinstall homebrew-ffmpeg/ffmpeg/ffmpeg --with-openssl@3
```

|---|:---:|
| RTMP / RTMPS | ✅ |
| SRT（libsrt） | ✅ |
| **WHIP muxer** | ✅ |

副次的な効果として、後述の x265 の応急処置も不要になった（新しいビルドは現行の

## 当初の結論（記録として残す）

**賄えない。** SRT・WHIP・drawtext を同時に満たすビルドが手元に存在しない。

## 検証結果

| 機能 | `homebrew-ffmpeg/ffmpeg` tap版 8.1.1 | `homebrew/core` の `ffmpeg@8` 8.1.2 |
|---|:---:|:---:|
| RTMP / RTMPS | ✅ | ✅ |
| **SRT（libsrt）** | ✅ | ❌ |
| **WHIP muxer** | ❌ | ✅ |
| **drawtext（libfreetype / libfontconfig）** | ✅ | ❌ |
| libx264 | ✅ | ✅ |
| h264_videotoolbox | ✅ | ✅ |
| AAC / libopus | ✅ | ✅ |
| testsrc2 / setpts / asetpts | ✅ | ✅ |

tap版のビルド構成（抜粋）：
```
--enable-gpl --enable-libx264 --enable-libx265 --enable-libopus
--enable-libfontconfig --enable-libfreetype --enable-libass
--enable-audiotoolbox --enable-videotoolbox --enable-libsrt
```
`--enable-openssl` が**無い**。

---

## WHIPが無い原因

FFmpegのWHIP muxerは **DTLS-SRTP** のハンドシェイクを行うため、TLSライブラリ（openssl / gnutls / mbedtls）を必要とする。configure時にそれが見つからないと WHIP muxer は無効化される。

紛らわしい点として、tap版でも `-protocols` には `tls` と `https` が出てくる。しかしこれは macOS の **SecureTransport** 由来であり、**DTLSは提供しない**。したがって「TLSは使えるのにWHIPが無い」という状態になる。

一方 `ffmpeg@8`（homebrew/core）は依存に `openssl@3` を持ち、`--enable-openssl` でビルドされているため WHIP muxer を備える。代わりに libsrt と freetype が入っていない。

## 実施した変更

`brew install ffmpeg@8` を実行した。この formula は **keg-only**（`/opt/homebrew/opt/ffmpeg@8/bin/ffmpeg` に隔離、PATHには入らない）なので、tap版 ffmpeg のバイナリ自体は置き換わらない。

> **ただし無害ではなかった。** 依存の x265 が更新され、tap版 ffmpeg が起動しなくなった。

第1段階では使わないため、不要なら削除してよい。第2段階の検証で再度使う可能性はある。


なお当初試した `brew install ffmpeg`（homebrew/core）は、tap版と同名formulaのため衝突してエラーになった。**tap版をアンインストールする必要はない**（第1段階に必要な機能はtap版に揃っているため）。

## 付録：`brew install ffmpeg@8` が tap版 ffmpeg を壊した件（2026-09-13）

### 症状

P0 の動作確認中、tap版 ffmpeg が起動しなくなっていた。

```
dyld[…]: Library not loaded: /opt/homebrew/opt/x265/lib/libx265.216.dylib
  Referenced from: /opt/homebrew/Cellar/ffmpeg/8.1.1/bin/ffmpeg
```

### 原因

`brew install ffmpeg@8` が依存の **x265 を 4.2 → 4.3 に更新**し、`/opt/homebrew/opt/x265` の
リンク先が 4.3 に切り替わった。4.3 が提供するのは `libx265.217.dylib` であり、
x265 4.2 に対してソースビルドされていた tap版 ffmpeg 8.1.1 は
`libx265.216.dylib` を探して失敗するようになった。

**ボトル（バイナリ）でインストールされる formula は依存を巻き込んで更新する。**
ソースビルドした tap 版と混在させるときの典型的な事故で、WHIP検証の副作用として踏んだ。

### 応急処置（実施済み）

x265 4.2 の keg 自体は残っていたため、旧 dylib への symlink を足して復旧させた。

```bash
ln -sfn ../../4.2/lib/libx265.216.dylib /opt/homebrew/Cellar/x265/4.3/lib/libx265.216.dylib
```

これは**応急処置**であり、x265 を更新・再インストールすると消える。

### 恒久対応

tap版 ffmpeg を現在の依存に対して再ビルドする。

```bash
brew reinstall homebrew-ffmpeg/ffmpeg/ffmpeg
```

どうせ再ビルドが必要なら、**同時に `--with-openssl@3` を付けて WHIP も有効にする**のが得
（第2段階の選択肢A）。この事故によって、案Aのコストは実質「再ビルド時間」だけに下がっている。

```bash
brew reinstall homebrew-ffmpeg/ffmpeg/ffmpeg --with-openssl@3
```

### 設計への反映

FFmpeg のパスを `config.toml` の `ffmpeg_path` にしてある判断は、この種の事故に対しても
有効だった。壊れていない別ビルドを指すだけで復旧できる。

## WHIP のローカル検証手順（2026-09-13 確立）

受け皿として mediamtx を使う。ボトル配布・依存なしで、不要になれば `brew uninstall mediamtx`。

```bash
brew install mediamtx
```

設定（`mediamtx-test.yml`）:

```yaml
webrtc: yes
webrtcAddress: :18889
webrtcLocalUDPAddress: 127.0.0.1:18189
webrtcIPsFromInterfaces: no          # ← 重要。理由は下記
webrtcAdditionalHosts: [127.0.0.1]   # ←
rtsp: yes
rtspAddress: :18554
rtspTransports: [tcp]
paths:
  all_others:
```

送出先は `http://127.0.0.1:18889/<任意のパス>/whip`。
受信確認は `rtsp://127.0.0.1:18554/<同じパス>` から引き戻す。

### 踏んだ罠：FFmpeg の WHIP muxer は ICE 候補を1つしか試さない

最初は DTLS ハンドシェイクが 5 秒でタイムアウトして繋がらなかった。debug ログを見ると:

```
transport=udp://fd7a:115c:a1e0::<host>:18189
DTLS handshake timeout=5000ms, cost=5035.87ms
```

`fd7a:115c:a1e0::/48` は **Tailscale の IPv6 レンジ**。mediamtx がローカルの全インターフェース
（Tailscale 含む）を ICE 候補として広告し、FFmpeg がその先頭を掴んで、そこへ DTLS を張ろうとして
失敗していた。**FFmpeg の WHIP muxer は完全な ICE を実装しておらず、候補を1つ選んで終わり**。

上の `webrtcIPsFromInterfaces: no` + `webrtcAdditionalHosts: [127.0.0.1]` で候補を絞ると
一発で通った。

実運用への含意：公開CDN（グローバルIPを1つ広告する）相手では問題になりにくいが、
**自前・社内のWHIPサーバー相手では候補の広告設定が効いてくる**。繋がらないときは
まずサーバー側が広告している候補を疑う。
