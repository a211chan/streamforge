> 送出中の映像を、送出側（このツール）で自分で見られるようにする。

---

## 1. 何のためのプレビューか

「プレビューが欲しい」には、実は目的の違う4つが混ざっている。分けて考えないと、
一番重い手段を全部に適用することになる。

| # | 確認したいこと | 必要なもの | 頻度 |
|---|---|---|---|
| 1 | 絵が出ているか（黒画・フリーズ・ソース選択ミス） | 1枚の静止画 | 開始直後と、たまに |
| 2 | オーバーレイが焼けているか／時計が進んでいるか | 1枚の静止画（時計が写る） | 開始直後 |
| 3 | 送っているビットストリーム自体が壊れていないか | 実ビットストリームのデコード | 稀 |
| 4 | 受信側との遅延 | 受信側の画面 | 別手段 |

**1 と 2 が9割。** どちらも毎秒1枚の静止画で足り、しかも時計が焼き込まれているので
「その絵がいつのフレームか」が絵そのものから読める。

4 は本ツールの対象外（憲章のスコープ表：受信側プレーヤー・品質計測は既存 analyzer の担当）。
本メモでも対象にしない。

---

## 2. 「重い」を3つに分ける

要望は「重くなりすぎるのは避けたい」。このプロジェクトで実際に痛い目を見たのは
CPU ではないので、そこを取り違えないようにする。

| 重さ | 症状 | このプロジェクトでの前例 |
|---|---|---|
| **A. サーバーCPU** | speed が 1.0 を割る | 実測済み。1080p60 veryfast で 9.6x の余裕がある。多少の追加は吸える |
| **B. 送出パイプラインへの干渉** | 片方のストリームが詰まって全体が止まる | **あり。** `arealtime` を足したら映像が128秒止まった。`max_interleave_delta` 既定で音声だけ117秒送出した |
| **C. 上り帯域の奪い合い** | speed が帯域比まで落ちる | **あり。** 8.1Mbps 要求に対し実測6.46Mbps、speed がぴったり 0.80x に張り付いた |

**本丸は B と C。** プレビューを遠隔（Tailscale 越しの MacBook）で見るなら、
プレビューの転送は送出と同じ上り回線を食う。フルレートのプレビューは
**それ自体が 0.80x 事件を再現しかねない**。観測が対象を壊す形になる。

## 3. 選択肢

| 案 | 仕組み | CPU | 上り帯域 | 遅延 | 送出への干渉 | 実物か |
|---|---|---|---|---|---|---|
| **A. 静止画** | フィルタを `split` し、片方を 1fps の JPEG にして1枚を上書き | ほぼ0 | ~90kbps | 1〜2秒 | 低 | エンコード**前**の絵 |
| **B. 実ストリーム** | `tee` で出力を分岐し、`-c copy` のまま LL-HLS をローカルに書く | ほぼ0 | **送出と同じ（8Mbps）** | 2〜4秒 | 中 | **そのもの** |
| **C. 低画質の別エンコード** | `split` した枝を 640p15 で別に H.264 化して HLS | 中 | ~600kbps | 2〜4秒 | 中 | エンコード前の絵 |
| **D. 受信側から引き戻す** | 配信先の再生URLを開く | 0（サーバー） | 0 | 数秒〜数十秒 | なし | 受信側の絵 |

D は本来もっとも正しい確認だが、再生URLが必ず手に入るとは限らず（顧客先インジェスト等）、
憲章のスコープ外でもある。**ブラウザで別タブを開けば済む**ので、実装するとしても
「登録済みの再生URLをリンクで置く」程度でよい。

### 実測（追加コスト）

testsrc2 1080p60 → libx264 veryfast 8000k + drawtext、`-f null` 出力、10秒×3回の中央値。
**他のジョブが動いている状態で測ったので絶対値は低め**（普段は9〜12x）。見るべきは差分。

| 構成 | 実時間比 | ベースライン比 |
|---|---|---|
| A0 プレビューなし | 11.6x / 11.5x（前後2回） | — |
| A1 JPEG 1fps 320px | 11.3x | **−2%** |
| A1b JPEG 5fps 480px | 11.4x | **−1.5%**（誤差の範囲） |
| A2 tee → HLS（`-c copy`） | 11.5x | **−0.9%** |
| A3 別エンコード 640p15 600k | 11.0x | **−5%** |

**CPU はどれも問題にならない。** 選択の軸は CPU ではなく、帯域と干渉リスク。

### 静止画の見え方とサイズ

実際のオーバーレイ（時計 h/16、設定行 h/28）を焼いた 1080p を縮小して確認した。

| 幅 | サイズ | 1fps での帯域 | 判読 |
|---|---|---|---|
| 320px | 7.2KB | ~60kbps | 時計は読める。下段の設定行は潰れ気味 |
| **480px** | **11.4KB** | **~90kbps** | 時計・設定行とも読める。**推奨** |
| 640px | 19.4KB | ~160kbps | 余裕はあるが、静止画にそこまで要らない |

## 4. 推奨案

**A（静止画）を既定で常時ON、B（実ストリーム）は開始時に選ぶオプション。**

理由：

1. 目的の9割（前掲 1・2）は静止画で足りる
2. 追加コストが誤差なので、**ON/OFF をユーザーに選ばせなくて済む**（憲章 Principle 1「人に選ばせない」）
3. FFmpeg の引数は起動時に固定されるため、**途中でプレビューを足すには送出を切るしかない**。
   「後から見たくなる」が普通に起きる以上、常時ONに倒せることが決定的に効く
4. B は「送っているビットストリームそのもの」を見る唯一の手段なので残す価値があるが、
   帯域を送出と奪い合う。**明示的に選んだときだけ**にする

### 副産物：映像停止の独立した検出器になる

静止画の更新時刻（mtime）が止まれば、それは**映像フレームが出ていない**ということ。
このプロジェクトが踏んだ「音声だけ進み、out_time は 1.00x のまま、映像だけ128秒停止」は、
`out_time` を見ていても表に出なかった。いまは `_video_rate()` で別に見ているが、
**静止画の更新間隔はそれとは独立した、目で見える裏取り**になる。

UI には「N秒前の絵」と出し、一定時間止まったら指摘に昇格させる。

## 5. 実装の要点

### 5-1. コマンド組み立て（`app/command.py`）

いまは `-vf` に一本道でフィルタを並べ、出力は1つ。プレビュー枝を足すには
`-filter_complex` + `split` に移す必要がある。**中核の変更**なので、ここが実装コストの本体。

```
-filter_complex "[0:v]<既存のvf>,split=2[main][pv];[pv]fps=1,scale=480:-2[pvout]"
-map "[main]" -map 0:a  <既存のエンコード設定>  -f mpegts <送出先>
-map "[pvout]" -c:v mjpeg -q:v 7 -update 1 -atomic_writing 1 -f image2 <data_dir>/preview/job-<id>.jpg
```

`split` は参照カウントだけでフレームを複製しないので、追加コストは
`fps` で間引いた後の `scale` と JPEG 化だけ。実測どおり誤差に収まる。

### 5-2. 検討中に踏んだ罠（実装前に分かってよかったもの）

| 罠 | 中身 | 対策 |
|---|---|---|
| **`-t` は出力ごと** | `-t 10` を1つ目の出力にだけ置くと、2つ目（プレビュー）は**無限に回り続ける**。lavfi 入力だとプロセスが終わらない。実際に止まらなくなった | タイムアウトは**両方の出力**に付ける |
| **上書き確認で止まる** | `image2` は既存ファイルがあると `Overwrite? [y/N]` を出して終了する。`-nostdin` と組むと即死 | `-y` を付ける（既存コマンドには無い） |
| **ちぎれた JPEG を読む** | `-update 1` は同じファイルを truncate して書き直すので、書き込み中に読むと壊れた絵になる | `-atomic_writing 1`（一時ファイル＋rename）。手元の FFmpeg 9.0.1 に存在を確認済み |
| **ベンチマークが壊れる** | `benchmark.to_null_output()` は「**末尾3つが `-f <muxer> <url>`**」を前提に出力を差し替える。出力が2本になると前提が崩れる | 計測用コマンドは `build_command(preview=False)` で組む。計測にプレビューは要らない |
| **`-c copy` では使えない** | passthrough はフィルタを通らないので `split` できない | passthrough のときは A を出さない。見たいなら B（tee）を選ばせる |
| **名前の衝突** | `preview` は既に「コマンドを確認」（`POST /api/jobs/preview`、`PreviewRequest`）で使われている | 新機能は `snapshot` / セルフビューなど別語にする |

### 5-3. 配信と UI

| 項目 | 方針 |
|---|---|
| 取得 | `GET /api/jobs/{id}/snapshot.jpg`（`Cache-Control: no-store`）。SSE に base64 で載せない（ログ経路を太らせるだけ） |
| 更新 | ブラウザ側で1〜2秒ポーリング。**`document.hidden` で止める**（タブを裏に回したら帯域を使わない） |
| 置き場 | `data_dir/preview/job-<id>.jpg`。ジョブ終了時に消す。最後の1枚だけ残して履歴・JSONレポートから参照する案もある |
| 鮮度 | mtime を返し、「3秒前」と出す。止まったら警告 |
| 音声 | 今回は対象外。必要なら将来、プレビュー枝で `astats` を拾ってレベルだけ数値で出す（絵より圧倒的に軽い） |

### 5-4. 失敗したときの扱い

* **A**：プレビュー出力が書けなくなる（ディスク満杯等）と、FFmpeg はプロセスごと終了する。
  つまり**プレビューの失敗で送出が落ちる**。ログを同じディスクに書いている以上
  条件は変わらないので許容するが、この一点は明記しておく。
* **B**：`tee` なら `onfail=ignore` で枝の失敗を無視できる。さらに `use_fifo=1` +
  `drop_pkts_on_overflow` を付けると、プレビュー枝の詰まりがエンコーダーを
  止めないよう切り離せる。**B を入れるなら必須の指定。**

### 実装して分かった、検討時に見えていなかったこと

| 見落とし | 実際 |
|---|---|
| 出力の順番はどちらでもよいと思っていた | **`-progress` は「最初の出力」の数字しか出さない。** プレビューを先に置くと、監視が毎秒1枚の枝を見てしまい `video_rate` が 1/30 に見える。実測: プレビューが先 → `frame=3 fps=0.74 total_size=N/A`、後 → `frame=110 fps=27.23 total_size=524288`。誤報（「映像が出ていません」）まで実際に出した |
| 「末尾を送出にしておけば計測側の前提が守れる」 | 上の理由で逆順にせざるを得ない。代わりに **計測用コマンドにプレビューが混ざっていたら `ValueError` で落とす**ことにした（黙って間違えるより落とす） |
| 計測（処理能力を測る）は正常に動いている前提だった | **壊れていた。** `-re` から `realtime` フィルタへ移した時点で、計測側の絞り外しが効かなくなり、どんな設定でも 0.8〜1.0 倍と出ていた。組み立て側に `pacing=False` を足して直した（640x360@30 ultrafast: 0.83x → 124.0x） |

## 7. 段4（実ストリームプレビュー）を見送った理由

段1〜3を動かしたうえで、**セルフプレビューは静止画だけにする**と決めた。

| 論点 | 判断 |
|---|---|
| 確認の頻度 | 「送っているビットストリームそのものが壊れていないか」を見たい場面は稀（§1 の #3）。日常の確認は静止画で足りている |
| 帯域 | 実ストリームは送出と同じレート。遠隔で見れば上り回線を奪い合い、**プレビュー自身が 0.80x 事件を引き起こしうる**（§2）。軽さを最優先にする方針と噛み合わない |
| リスク | `tee` は**送出パスそのもの**を差し替える。RTMP / SRT / WHIP で muxer ごとの挙動が違い、実インジェスト先での確認なしに入れる変更ではない |
| 代替 | 受信側の確認が要る場面では、既存の analyzer を併用する（憲章のスコープどおり） |

必要になったら、実エンドポイントで試せるタイミングで `onfail=ignore` +
`use_fifo` 込みで入れる。そのときはこのメモの §3・§5-4 が出発点になる。

## 8. 対象にしないこと

* 受信側の品質計測・遅延計測（既存の analyzer が担当。憲章のスコープ表どおり）
* ブラウザでの音声モニタリング
* 複数ジョブ同時プレビュー（送出は1本という前提を変えない）
* 実ストリーム（ビットストリームそのもの）のプレビュー — 上記のとおり見送り
