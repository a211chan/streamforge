# StreamForge — プロダクト憲章

> サーバー完結型ライブエンコードテスト基盤
> RTMP / SRT / WebRTC(WHIP) のどれか **1本** を、設定工数ゼロに近い形で送出する

改訂：2026-09-13（FFmpeg再ビルドにより WebRTC(WHIP) を前倒しで実装。3プロトコル対応完了）

---

## 1. Context — なぜ作るか

### 現状の課題

| 課題 | 具体的に何が起きているか |
|---|---|
| 起動が面倒 | テスト送出のたびにOBSを立ち上げ、シーンとソースを選び、設定タブでプロトコルを選ぶ。実作業は「開始を押す」だけなのに、そこまでが長い |
| 設定工数 | プロトコルごとに設定画面が別。SRTのstreamid/latency/passphraseは毎回手打ち。設定ミスの切り分けに時間を取られる |
| 再現性がない | 「前回どのビットレート・GOP・presetで送ったか」がOBSのプロファイルに埋もれ、記録として残らない |
| 長時間試験が回せない | 端末を占有する。24時間耐久や夜間の疎通維持テストが事実上できない |
| 遅延計測が手作業 | 送信側の時計と受信側の再生画面を並べてスマホで撮る、という原始的な方法に頼っている |
| WebRTC送出手段が乏しい | OBS 30+ のWHIP対応はあるが、RTMP/SRTと**同じ操作感**で切り替えられない |

### 一言でいうと

**「配信先URLを貼って、開始を押す。それだけ」**を実現する。
プロトコルの選択も、エンコード設定の再入力も、ユーザーの仕事から外す。

---

## 2. Vision — 何を実現するか

Mac mini 上に常駐するWebアプリ。ブラウザから以下を行う。

1. 送出先URLを**貼る** → URLの形からプロトコル（RTMP / SRT / WHIP）を**自動判定**する
2. 映像ソースを **ローカルファイルのループ再生** / **外部の常時ライブソース** / **内蔵テストパターン** から選ぶ
3. エンコード条件は**既定値のまま使える**。変えた場合は**自動でテンプレートとして保存**され、次回から選べる
4. 「開始」を押す → FFmpegが送出を開始
5. 受信側で再生すると、映像に **ミリ秒精度の時計** と **エンコード設定** が焼き込まれている

### スコープの線引き

| 対象に**する** | 対象に**しない** |
|---|---|
| 同時に **1本** の送出 | 複数出力・プロトコル並列送出（将来の拡張候補） |
| **RTMP / SRT(caller) / WebRTC(WHIP)** — 3プロトコルとも実装済み | RTP, NDI, ST 2110, RIST |
| URLからのプロトコル自動判定 | プロトコルを人に選ばせるUI（手動上書きは残す） |
| エンコード条件の自動テンプレート保存 | 手動でのプロファイル命名・管理を必須にすること |
| CPU（libx264 / VideoToolbox）エンコード | ABRラダー生成、パッケージング |
| Mac mini 上での個人利用 | 現段階でのVPS常駐・マルチユーザー |
| **送出先を限定しない**（Ceeblue / MOGUL / YouTube Live / 自社サーバー / 顧客先） | 送出先ごとの専用UI・専用プリセット |
| 送出（エンコーダー）側の代替 | 受信側プレーヤー・品質計測（→ 既存の WebRTC analyzer / HLS analyzer が担当） |

## 3. 稼働環境の方針（重要な前提変更）

**第1段階：Mac mini M4（母艦）での個人利用**

- 通信量コストを避けるため、当面VPSは使わない
- Mac mini は常時稼働しており、長時間送出の置き場所としてそのまま使える
- アクセスは Tailscale 経由。アプリは `127.0.0.1` にバインドし、外部公開しない
- 常駐は launchd（`launchctl`）で管理する

**第2段階：Linux / VPS への移植（パブリック公開時）**

移植を「後からの作業」にしないため、第1段階から次を守る。

| 制約 | 理由 |
|---|---|
| OS固有パスをコードに埋めない（フォント・メディア・ログはすべて設定ファイル経由） | macOSとLinuxでフォントパスが違う。ここを直書きすると移植時に必ず壊れる |
| フォントはリポジトリに同梱する | 同じ `drawtext` 指定が両OSで同じ見た目になる |
| エンコーダーは差し替え可能にする（`libx264` ⇄ `h264_videotoolbox`） | Macではハードウェアエンコードが使えるが、Linux VPSでは使えない |
| Docker化は「できる状態」にしておくが、Macでは必須にしない | Mac上でDocker Desktopを常駐させるのはメモリの無駄。移植時にDockerfileを起こせる構成にとどめる |
| 依存はHomebrewと`requirements.txt`だけで完結させる | 環境構築を1コマンドに保つ |

## 5. Principles — 判断に迷ったときの指針

1. **人に選ばせない** — URLから分かることは自動で判定する。分からないときだけ聞く
2. **設定は「変えたら勝手に残る」** — 名前を付けて保存する作業をユーザーに強いない
3. **失敗はUIで説明する** — FFmpegのstderrをそのまま出さず、「SRTのハンドシェイクが通っていません（passphrase不一致の可能性）」まで翻訳する
4. **サーバーは落ちても壊れない** — プロセスの孤児化を防ぐ。再起動後に「動いているつもり」の幽霊ジョブを残さない
5. **記録が残る** — 実行したコマンド・条件・開始終了時刻を必ず保存する。「あのときの設定」を再現できる
6. **Macに閉じない** — 動く場所がMacというだけで、コードはLinuxを向いて書く

## 6. Success Metrics — 何をもって成功とするか

| 指標 | 目標 |
|---|---|
| URLを貼ってから送出開始までの操作時間 | **30秒以内**（プロトコル選択・設定入力の工程がゼロ） |
| 新規インジェスト先の疎通確認にかかる時間 | 15分 → **3分** |
| テスト送出のためにOBSを起動する回数 | **0回** |
| 24時間連続送出の完走率 | **95%以上**（自動再接続込み） |
| 2回目以降の送出で設定入力が必要な回数 | **0回**（テンプレート自動保存が効いている状態） |

## 7. Risks — 想定される落とし穴

| リスク | 対応方針 |
|---|---|
| **URL自動判定の誤り** | 判定結果を必ずUIに表示し、ワンクリックで手動上書きできるようにする。「勝手に決めて黙って間違える」のが最悪 |
| **WebRTC送出の実装手段**（解消済み） | Homebrew版FFmpegにWHIP muxerが含まれていなかった（原因は `--enable-openssl` 不在＝DTLS不可）。`--with-openssl@3` 付きで再ビルドし、**SRT・drawtextと両立する1バイナリで解決**（FFmpeg 9.0.1、ビルド1分18秒）。詳細は `環境検証メモ.md` |
| **WHIPのICE候補** | FFmpegのWHIP muxerは完全なICEを実装しておらず、**候補を1つしか試さない**。サーバーがVPN等の到達不能なアドレスを先に広告すると繋がらない。自前サーバー相手のときはサーバー側の広告設定を疑う |
| **テンプレートが増えすぎる** | 自動保存は便利だが放置すると一覧が汚れる。内容ハッシュで重複排除し、最終使用日でLRU整理する（ピン留めは対象外） |
| **Mac固有実装への引きずられ** | VideoToolbox等のMac固有機能は「差し替え可能な実装」として隔離し、既定は libx264 にする |
| **外部ライブソースの利用規約** | 既定は「ライセンスが明示された公開テストストリーム」に限定。任意URLは自己責任の上級者オプション |
| **プロセスの暴走・孤児化** | ジョブは既定2時間のタイムアウトを持つ。プロセスグループ単位で確実に停止する |
| **passphrase等の機密** | 秘匿値は暗号化保存。UIではマスク表示、ログには出さない |
| **Public化時の情報漏れ** | 機密はすべてDB（`.gitignore`済み）に置き、リポジトリには一切入れない。ドキュメントの例示は `example.com` に統一。`公開前チェックリスト.md` で公開時に検査する |

## 8. 非機能要件

| 項目 | 方針 |
|---|---|
| 稼働環境（現在） | Mac mini M4 / macOS / Apple Silicon（arm64）、`homebrew-ffmpeg/ffmpeg` tap版 FFmpeg 9.0.1（`--with-openssl@3`／libsrt・drawtext・WHIP 有効） |
| 稼働環境（将来） | Ubuntu系 Linux + Nginx。コードの変更なしに移せることを目標とする |
| 待受 | `127.0.0.1:8080`。外部からは Tailscale 経由でのみ到達 |
| 認証 | 現段階では不要（ローカルバインド + Tailscale で担保）。公開時にBasic認証を追加 |
| データ保持 | ジョブ履歴90日、ログは1ジョブあたり末尾5MBまで |
| 常駐 | launchd（macOS）/ systemd（Linux）。どちらも「起動コマンド1行」で済む構成にする |
| リポジトリ | GitHub 個人 / **Private**（`a211chan/StreamForge`）。将来 Public 化する前提で、最初のコミットから機密を含めない |
| ライセンス | MIT。FFmpegは外部プロセスとして呼ぶだけでリンクしないため、GPLビルドを使っても本体はMITで配布できる |

## 10. ブランド

<img src="images/brand/icon-1024.png" alt="" width="180">

鍛冶場のタヌキ。刀を打つ手つきで配信を試す、という見立て。
原本と派生物の作り方は [assets/brand/README.md](../assets/brand/README.md)。

判断に迷ったときの線引きは3つ。

**1. マスコットはカラーでしか出さない。**
単色に落とすと輪郭の情報量が多すぎて、22px では絵として判読できない
（64px まで試して駄目だった）。小さく置きたいなら顔だけを切り出す。

**2. 画面の中でマスコットを出すのは light と dark だけ。**
terminal の緑一色、typewriter の赤インク一色、tactical の艶のない面に
ネイビーとオレンジのタヌキを置けば、壊れるのはシーンの世界観のほうである。
この3シーンでは、そのシーンが既に持っている記号（プロンプト、隅の括弧、罫線）で
題字を立てる。ブランドを我慢させるのではなく、**シーンの語彙に翻訳する**。

**3. ブランド色を `theme.css` に入れない。**
画面の色を決めるのはセマンティックトークンだけ、という原則が先にある。
ブランド色を採用するなら、`tools/check-contrast.py` と `tools/palette-search.py` を
通し、5シーンすべてで下限を満たすことを確かめてから。版下の値をそのまま
`--accent` に入れてよい理由は無い。
